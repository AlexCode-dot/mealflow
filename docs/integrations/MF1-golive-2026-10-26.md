# MF1 go-live — turning on "Koppla MealFlow" from Personal OS

Date: 2026-10-26 · Branch: `personal-os/mf1-golive` (fast-forward of `personal-os/mf1` from `main` d5f06b2)
· Task: Personal OS `docs/v1/GL1 MealFlow Go-Live.md`, section **GL1b** · ADR PA-011.

This is the runbook for **Alexander**. Nothing here was deployed and no real value was generated or
committed: the client secret is generated by you, on the server, and lives only in `.env.prod`.

---

## 1. What this branch adds on top of `personal-os/mf1`

| File | Change |
| --- | --- |
| `infra/docker-compose.prod.yml` | passes `PERSONAL_OS_OAUTH_CLIENT_ID`, `PERSONAL_OS_OAUTH_CLIENT_SECRET`, `PERSONAL_OS_OAUTH_REDIRECT_URIS` from `.env.prod` to `identity-service` |
| `infra/.env.prod.example` | documents the three variables, empty, with how to fill them |
| `services/identity-service/.../oauth/config/OAuthClientConfigurationTest.java` | pins the off switch: blank or partial config registers **no** OAuth client |

That is all. `personal-os/mf1` itself (the OAuth provider in identity-service, `/integrations/v1` in
app-api, the "Kopplade appar" screen in the app) is unchanged — it was built and QA'd on 2026-10-11,
see `MF1-report-2026-10-11.md` and `QA-MF1-2026-10-11.md`.

**No Caddy change is needed.** `identity.<DOMAIN>` already reverse-proxies the whole host to
identity-service, so `/oauth2/authorize`, `/oauth2/token`, `/oauth2/revoke`, `/oauth/login` and the
consent page are routed as soon as the service is deployed.

**No app-api variable is needed.** `/integrations/v1` validates connected-app tokens through
`IDENTITY_JWKS_URI` + `IDENTITY_SHARED_MONGODB_URI`, both already in the prod compose file; its new
settings (`INTEGRATIONS_GRANT_CACHE_SECONDS`, `INTEGRATIONS_TIMEZONE`,
`RATE_LIMIT_INTEGRATIONS_PER_MINUTE`) all have working defaults.

### The off switch

`identity-service` registers the Personal OS OAuth client **only** when client id, client secret and
at least one redirect URI are all non-blank (`OAuthClientProperties.isConfigured()`). Docker compose
substitutes a variable that is missing from `.env.prod` as the empty string, so "not set on the
server" arrives as blank and the client is not registered — `/oauth2/authorize` then has nothing to
authorize and refuses the request. `OAuthClientConfigurationTest` pins that for every blank/partial
combination.

One thing that can mislead you while checking: an **unauthenticated** `/oauth2/authorize` redirects to
MealFlow's login page before the client is looked up at all, configured or not. So reaching the login
page proves nothing about whether the connection is on — §4.2 is the check that does.

So: **merging and deploying this branch without touching `.env.prod` changes nothing for existing
MealFlow users.** You can do step 2 now and step 3 whenever you like.

## 3. Turn the connection on

### 3.1 Generate the client secret (on the VPS, once)

```bash
openssl rand -hex 32
```

Keep this value. It goes in **two** places and nowhere else: MealFlow's `.env.prod` and Railway's
`POS_MEALFLOW_CLIENT_SECRET`. Never into git, never into a chat or an issue.

### 3.2 Put the three values in `/opt/mealflow/infra/.env.prod`

```bash
nano /opt/mealflow/infra/.env.prod
```

Append (the file already has every other variable; `.env.prod` is gitignored):

```dotenv
PERSONAL_OS_OAUTH_CLIENT_ID=personal-os
PERSONAL_OS_OAUTH_CLIENT_SECRET=<the openssl value from 3.1>
PERSONAL_OS_OAUTH_REDIRECT_URIS=https://personal-os-api-production-7b0c.up.railway.app/connections/mealflow/callback
```

- **`CLIENT_ID`** — any stable opaque string; `personal-os` is fine. It must equal Railway's
  `POS_MEALFLOW_CLIENT_ID` exactly.
- **`CLIENT_SECRET`** — the value from 3.1, equal to Railway's `POS_MEALFLOW_CLIENT_SECRET`. MealFlow
  stores only a hash of it in memory; the raw value never leaves `.env.prod`.
- **`REDIRECT_URIS`** — comma-separated, **exact** `https` URIs, no trailing slash. Personal OS builds
  it as `<POS_PUBLIC_ORIGIN>/connections/mealflow/callback` (`packages/connectors/oauth.ts`: "exact,
  `<this instance's origin>/connections/<id>/callback`, never a request field") and sends
  `redirect_uri` on both `/oauth2/authorize` and `/oauth2/token`. **Confirm `POS_PUBLIC_ORIGIN` on
  Railway before pasting** — the value above is GL1's reading of the Railway host, and an inexact
  value fails the flow closed with `invalid_request` at the authorize step. If the Personal OS origin
  ever changes, add the new URI here (comma-separated) before switching.

Then redeploy so the container picks the variables up:

```bash
cd /opt/mealflow/infra
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d identity-service
```

### 3.3 Railway (Personal OS side — needs GL1a deployed)

| Variable | Value |
| --- | --- |
| `POS_MEALFLOW_CLIENT_ID` | same as `PERSONAL_OS_OAUTH_CLIENT_ID` |
| `POS_MEALFLOW_CLIENT_SECRET` | same as `PERSONAL_OS_OAUTH_CLIENT_SECRET` |
| `POS_MEALFLOW_BASE_URL` | `https://api.<DOMAIN>` — the `/integrations/v1` host |
| `POS_MEALFLOW_AUTH_URL` | `https://identity.<DOMAIN>` — the OAuth host (GL1a's split-host variable) |

MealFlow serves OAuth on `identity.<DOMAIN>` and the integration API on `api.<DOMAIN>`, and the token
`iss` is `https://identity.<DOMAIN>`. Without GL1a's `POS_MEALFLOW_AUTH_URL`, Personal OS assumes one
host and the flow cannot work — so **deploy GL1a first**.

## 4. Check it works

### 4.1 The variables reached the container

```bash
cd /opt/mealflow/infra
docker compose -f docker-compose.prod.yml exec identity-service \
  printenv PERSONAL_OS_OAUTH_CLIENT_ID PERSONAL_OS_OAUTH_REDIRECT_URIS
```

Both printed, non-empty. Do **not** print the secret.

### 4.2 The client is actually registered (no browser needed)

Read the three values out of `.env.prod` rather than typing them — this keeps the secret out of your
shell history and out of `ps`. (Do not `source .env.prod`: the Mongo URIs in it contain unquoted `&`.)

```bash
cd /opt/mealflow/infra
CID=$(grep -E '^PERSONAL_OS_OAUTH_CLIENT_ID='      .env.prod | cut -d= -f2-)
CSEC=$(grep -E '^PERSONAL_OS_OAUTH_CLIENT_SECRET=' .env.prod | cut -d= -f2-)
RURI=$(grep -E '^PERSONAL_OS_OAUTH_REDIRECT_URIS=' .env.prod | cut -d= -f2- | cut -d, -f1)

curl -s -w '\n%{http_code}\n' https://identity.<DOMAIN>/oauth2/token --config - <<EOF
user = "$CID:$CSEC"
data = "grant_type=authorization_code&code=not-a-real-code&redirect_uri=$RURI"
EOF

unset CSEC
```

- `{"error":"invalid_grant"}` (HTTP 400) → **correct.** The client id and secret were accepted; only
  the fake code was rejected. This is the signal you want.
- `{"error":"invalid_client"}` (HTTP 401) → the id or the secret does not match what is in
  `.env.prod`, or the container did not restart.

### 4.3 The consent page loads

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://identity.<DOMAIN>/oauth/login
```

`200` → the server-rendered OAuth pages (login / sign-up / verify / consent, Thymeleaf) are live.
This says nothing about the client registration (see §1) — it only proves the templates render.

For the consent page itself, open this in a **phone browser** (one line, `<DOMAIN>`, `<CLIENT_ID>` and
the redirect URI filled in):

```
https://identity.<DOMAIN>/oauth2/authorize?response_type=code&client_id=<CLIENT_ID>&redirect_uri=<exact redirect URI>&scope=recipes.read&state=manual-check&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256
```

Expected: MealFlow's login page → log in with your own MealFlow account → the consent screen,
headed "Koppla Personal OS till MealFlow", listing the scope you asked for in plain language (Swedish
if the browser asks for Swedish, English otherwise), with **Tillåt** and **Neka**. Press **Neka** — the manual check
is over at that point; it redirects to Personal OS with `error=access_denied` and issues nothing.
(The `code_challenge` above is the published RFC 7636 example value; it is a throwaway and cannot be
used to complete a flow, since only Personal OS holds a matching verifier.)

### 4.4 The real thing

In Personal OS: **Mer › Dina appar › MealFlow › Koppla** → MealFlow's consent page → **Tillåt** →
back in Personal OS it should read **"Kopplad"**.

In MealFlow: **Inställningar › Kopplade appar** now lists Personal OS, with the granted scopes and
**Ta bort åtkomst**. Removing access takes effect on the Personal OS side within 30 seconds
(`INTEGRATIONS_GRANT_CACHE_SECONDS`).

## 5. Turning it off again

Blank the three values in `/opt/mealflow/infra/.env.prod` and
`docker compose --env-file .env.prod -f docker-compose.prod.yml up -d identity-service`. No client is
registered, so no new consent and no token refresh can happen. Existing grant documents stay in
`oauth2_authorizations` and become usable again if you put the same id and secret back; to drop them
for good, each user can remove access from **Inställningar › Kopplade appar**.

Rotating the secret: generate a new one, update `.env.prod` and Railway, redeploy both. Existing
refresh tokens keep working (they are bound to the grant, not to the secret); only Personal OS needs
the new secret to use them.

## 6. What does not change for existing MealFlow users

- Nothing at all while the three variables are empty — see §1.
- Once they are set, nothing changes until a user goes through the consent flow themselves. There is
  no default grant and no pre-existing consent.
- First-party login is untouched: `/auth/*` and `/api/**` keep refusing any token that carries `aud`
  or `client_id`, so a Personal OS token can never act as a MealFlow app session (MF1, QA'd).
- One thing to be aware of, from `personal-os/mf1` rather than from this branch: identity-service's
  new page filter chain also matches `/error`, so an unmatched error dispatch renders its real status
  instead of the API chain's blanket 401. Deliberate (an unregistered `redirect_uri` has to surface
  its own error), and covered by `QaMf1OAuthAdversarialIT`.

## 7. Open decisions for you

1. **The redirect URI.** The value in §3.2 is GL1's reading of the Railway host, not something this
   session could verify. Read `POS_PUBLIC_ORIGIN` off Railway and use `<that>/connections/mealflow/callback`.
2. **Order.** GL1a (`POS_MEALFLOW_AUTH_URL`) must be deployed on Railway before step 3.3, otherwise
   Personal OS points OAuth at `api.<DOMAIN>` and the flow 404s.
3. **Client id string.** `personal-os` matches the internal registered-client id MealFlow already uses
   on grants (`OAuthScopes.PERSONAL_OS_REGISTERED_ID`), which keeps logs readable. Any other stable
   string works as long as both sides match.
