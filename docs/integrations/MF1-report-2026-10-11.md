Date: 2026-10-11 · Branch: `personal-os/mf1` (from `origin/main` d5f06b2f) · Brief: Personal OS
`docs/v1/MF1 MealFlow OAuth Provider and Integration API.md`, ADR PA-011.
Local/offline only: no deploy, no production config values, no real user data, no secrets committed.

## What was built

### identity-service — authorization server

- **Spring Authorization Server** (Spring Security 7.0 / Boot 4 starter) — no hand-rolled protocol code.
- **Grant:** authorization code + PKCE. S256 is required; missing or `plain` PKCE is refused.
- **Client:** one confidential client `personal-os`, read from env. Its secret is hashed in memory. The
  redirect URI must match exactly. Client auth is basic or post.
- **Scopes:** `recipes|mealplan|shoppinglist` × `.read|.write`.
- **Access token:**
  - JWT, 5 min
  - Claims `aud=mealflow-integrations`, `client_id`, `gid` (grant id), `scope`
  - Signed with the existing RSA key (kid `mealflow-identity-rs256`)
- **Refresh token:** 30 days, rotates on every use.
- **Refresh-token reuse detection:** the Mongo store keeps hashes of rotated-out refresh tokens.
  Presenting one again deletes the whole grant (the family) and writes a
  `security.token_reuse_detected` audit event.
- **Revocation:** `/oauth2/revoke` (RFC 7009).
- **Mongo grant/consent stores** (`oauth2_authorizations`, `oauth2_authorization_consents`): token values
  are never stored, only SHA-256 hashes. Protocol decisions stay in the library; the store only maps
  data.
- **Browser pages** (Thymeleaf, i18n EN default + SV via `Accept-Language`):
  - Login with existing MealFlow accounts: argon2, verified email, disabled/deleted blocked
  - Sign-up, then email code (OTP via the existing `EmailVerificationService`)
  - Consent screen naming each scope in plain language. The user can untick scopes or deny
    (→ `access_denied`)
  - CSRF, session fixation protection, default security headers
- **Rate limits:**
  - `/oauth/login`, `/oauth/signup` and `/oauth/verify*` share the existing per-IP buckets of
    `/auth/login`, `/auth/register` and `/auth/verify-email`. The limiter runs before CSRF, so floods
    are counted.
  - New buckets: token 30/min, revoke 30/min, authorize 60/min.
- **First-party API hardened:** tokens carrying `aud` or `client_id` are rejected (e.g. a Personal OS
  token cannot call `DELETE /account`).
- **Connections API:** users can see and revoke Personal OS access with `GET /account/connections` and
  `DELETE /account/connections/{clientId}` (first-party token). Account deletion removes all grants and
  consents.
- **Audit:** `oauth.consent_granted`, `oauth.token_issued`, `oauth.token_revoked`,
  `oauth.access_revoked_by_user`, `security.token_reuse_detected`, and `auth.*` events with
  `channel=oauth`. No token values are written.

### app-api — resource server + `/integrations/v1`

- **Separate filter chain** for `/integrations/**`, ordered first:
  - JWKS decoder plus issuer/exp/nbf checks
  - `aud` must be `mealflow-integrations`, `client_id` and `gid` must be present
  - **Grant-active check** against identity's `oauth2_authorizations` (doc exists, `principalName == sub`,
    not `revoked`), with a ≤ 30 s cache → disconnect takes effect within 30 s
- **Scope enforcement** per endpoint: missing scope → 403, bad token → 401.
- **Endpoints:**
  - recipes: list/search with cursor paging, get, create, PATCH
  - meal plan: current and next week, add/remove entry
  - shopping lists: list, get, add/remove/check/uncheck item
- **Idempotency:** `Idempotency-Key` required on every write. Records are inserted before the write runs
  (unique index per user+client+key, 24 h TTL), so a key can never apply twice.
  - Same key, same request → stored response replayed with `Idempotency-Replayed: true`
  - Same key, different request → 422
  - Original still in flight → 409
  - Failed write → key released for retry
- **ETag / `version`** (epoch millis of `updatedAt`). `If-Match` → 412 on mismatch. Writes are
  compare-and-set in Mongo, so there is no check-then-write race.
- **Isolation:** every query filters on `sub`. Another user's ids → 404.
- **First-party `/api/**` chain:** now rejects connected-app tokens.
- **Rate limit:** `/integrations/**` 60/min per user+client (separate from `/api`). One
  `integration_audit` log line per request, without token values or bodies.

### Test infra fix (app-api)

`support/MongoTestContainerConfig` was switched to the singleton-container pattern that identity-service
already uses. The per-class `@Container` lifecycle plus Spring's cached context made existing ITs
(`ProfileControllerIT`, `IntegrationTokenAuthIT`) fail with "Mongo connection refused" once more test
classes shared the context. This is a test-only change, and an external `*_MONGODB_URI` still takes
precedence.

## Run locally

1. Follow `LOCAL_DEV.md` (Docker Mongo, RSA keys in `services/identity-service/.secrets`).
2. Start identity-service with the client configured. Use a locally generated value for the secret and
   never commit it:
   ```bash
   export PERSONAL_OS_OAUTH_CLIENT_ID=personal-os
   export PERSONAL_OS_OAUTH_CLIENT_SECRET="$(openssl rand -hex 32)"
   export PERSONAL_OS_OAUTH_REDIRECT_URIS=http://localhost:3000/connections/mealflow/callback
   ```
3. Open `http://localhost:8081/oauth2/authorize?response_type=code&client_id=personal-os&redirect_uri=…&scope=recipes.read%20mealplan.read&state=…&code_challenge=…&code_challenge_method=S256`.
4. Exchange the code at `POST /oauth2/token` (basic auth), then call
   `http://localhost:8082/integrations/v1/recipes`. app-api needs `IDENTITY_SHARED_MONGODB_URI` pointing
   at the identity DB for the grant check.

## Open items / notes for QA

1. **Universal-link consent in the MealFlow app** is not built. The flow currently runs on MealFlow's web
   pages (login/sign-up/consent). The ADR's "opens the app via universal link, Face ID" needs app-side
   routing (associated domains plus an in-app consent screen that completes `/oauth2/authorize` with the
   app session). This is a separate pass.
2. **Forgot password** on the OAuth login page only links the user to the app ("reset it in the MealFlow
   app"). There is no web reset flow yet.
3. **Revocation latency:** access tokens are self-contained JWTs (5 min). app-api's grant check caps the
   effective lifetime after disconnect or reuse at ≤ 30 s. Personal OS should still treat 401 as
   "reconnect or refresh".
4. **`aud` is serialized as a string** (single audience, RFC 7519). Clients must accept a string or an
   array.
5. **Not covered by tests:**
   - the 409 "same key still in flight" path (implemented, not exercised: needs a concurrency test)
   - the Expo screen (typecheck/lint only, no device run)
   - the OAuth pages' visual design (rendering is checked in tests, not visually reviewed)
6. **Production:** nothing is enabled until the three `PERSONAL_OS_OAUTH_*` values are set in the secret
   store. MealFlow's issuer URL must be the public HTTPS identity URL so `iss` matches app-api's
   `IDENTITY_JWT_ISSUER`. Sessions for the OAuth pages are in-memory (single identity instance); scaling
   out needs sticky sessions or a shared session store.
7. Process note: the session was interrupted for about 3 h mid-pass (the app-api sub-worker stopped
   mid-run). Its partial work was reviewed, fixed (week validation 404, test URL, test-container
   lifecycle) and fully re-run here. The wall-clock time box was exceeded because of the interruption,
   not because of extra scope.
