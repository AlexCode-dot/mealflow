## What changed

### 1. `POST /integrations/v1/shopping-lists/active` (new, additive)

| | |
|---|---|
| Scope | `shoppinglist.write` (existing matcher `V1/shopping-lists/**` for non-GET; no security config change) |
| Headers | `Idempotency-Key` required (same `IdempotencyService` as the other writes); no body; `If-Match` not used |
| Active list exists | **200**, body and `ETag` exactly as `GET /shopping-lists/{id}` (same `respond(...)` helper). The list is not written |
| No active list | **201**, a new empty active list — same fields as the app's `ensureActiveList` (`title: null`, `weeklyPlanId: null`, no items) — with `Location: /integrations/v1/shopping-lists/{id}` and `ETag` |
| Concurrent calls | Exactly one list; one caller gets 201, the rest 200 with the same id |
| Replayed key | The first response (status, body, `ETag`, `Location`) + `Idempotency-Replayed: true`; no second list |
| Isolation, rate limit, audit, problems | Unchanged machinery: all queries on the token's `sub`; `/integrations/**` rate-limit filter and `IntegrationAuditFilter` apply as to every route; errors are problem+json |

Code: `IntegrationShoppingListController#ensureActive`, `IntegrationShoppingListService#ensureActive` →
`ShoppingListService#ensureActive`.

### 2. At most one active list — enforced in the domain service, for app and integration API

- **Per-user lock** `ActiveShoppingListLock` (new, `shoppingLists/service`). A lease document per user in a new
  collection `shopping_list_locks` (`_id = userId`): acquire = `findAndModify` upsert on
  `{_id: userId, lockedUntil < now}`; a live lease from another holder collides on `_id` and the caller retries
  (20 ms, up to 5 s); release deletes only the caller's own lease; a crashed holder's lease expires after 10 s.
  It works across app-api instances and does not depend on the existing data being clean (a partial unique index
  on `{userId, status: ACTIVE}` would fail to build if production already has a user with two active lists —
  which the PATCH bug below makes possible). If the wait runs out: `ShoppingListBusyException` → **409**
  problem+json (app and integration API). The collection needs no index and is empty except while a request runs.
- `ShoppingListService.ensureActive(userId)` (public, returns `ActiveList(list, created)`) runs
  "find the most recently updated active list, else create one" under the lock. The private `ensureActiveList`
  used by `createOrMerge`, `patchList` (archive) and `deleteList` now goes through it, so the app's own paths are
  serialised with the integration route too. New lists get `createdAt/updatedAt` truncated to milliseconds (what
  Mongo stores), so the 201 body equals a later GET.
- **PATCH fix** (`PATCH /api/shopping-lists/{id}`, `status: active` on an archived list): under the same lock,
  every *other* active list of the user is archived (`updateMulti` on `status` + `updatedAt` only, items are not
  rewritten), then the list is made active. Result: exactly one active list, the one just activated (the app's
  "current" list becomes this one). Status changes (both directions) run under the lock; title-only PATCH does not.
  Activating a list that is already active is a no-op, as before.

**App UI:** nothing is affected. The Expo app only ever PATCHes `status: 'archived'`
(`apps/expo-app/src/features/shopping-lists/hooks/useShoppingListDetailsScreen.tsx:394`); there is no
"restore/activate" action in the UI. The overview takes `list('active')[0]` and creates one if empty
(`useShoppingListOverviewScreen.tsx:91-110`), which matches "one active list". Response shapes are unchanged.

## Deploy

app-api only; no config, env var or migration. A new, normally empty Mongo collection `shopping_list_locks` is
created on first use. As in `MF1-golive-2026-10-26.md`:

```bash
railway up services/app-api --path-as-root --service app-api
```

Users who already have two active lists (possible via the old PATCH path) keep working: reads pick the most
recently updated, and the next activation through PATCH archives the other one. No data is rewritten on deploy.
