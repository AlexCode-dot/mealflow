## STOP check: the app's generator

The brief says to stop if the generator can only make a new list, or calls a paid LLM per request without a
bound. **Neither applies**, so I went ahead:

- **It adds to an existing list.** `ShoppingListService#createOrMerge(userId, weeklyPlanId, replace=false, …)`
  (`POST /api/shopping-lists` with `weeklyPlanId`) merges the plan into the user's **active** list
  (`ensureActiveList`), via `ShoppingListGenerator#mergePlan(existingItems, plan, recipes, normalizedNames)`.
- **LLM calls: at most 2 per generation, each one batched and capped, and fail-soft.**
  - `LlmItemNameNormalizer#normalize`: **1 call** with every name the merge compares (plan + unchecked
    list lines), capped at 150 names (`MAX_NAMES_PER_CALL`). It also returns aisles.
  - `ItemCategoryResolver#applyCategories` → `LlmItemCategorizer#categorize`: **0 or 1 call**, only for
    names the keyword lookup and the normalizer left without an aisle, capped at 60.
  - With no `ANTHROPIC_API_KEY` there are **no calls**; on any failure the merge uses exact names and `OTHER`.
  - Files: `services/app-api/src/main/java/com/mealflow/appapi/shoppingLists/service/{ShoppingListService,
    ShoppingListGenerator, LlmItemNameNormalizer, ItemCategoryResolver, LlmItemCategorizer}.java`.

**For the new route** (see below): 1 normalization call, then 0–1 categorization calls per write attempt.
The write is retried at most 3 times if the list changes during the merge, so the worst case is
**1 + 3 = 4 calls**. In practice it is **≤ 2**: the IT measures 1 for a new list and ≤ 2 when merging into an
existing list. A replayed key, a 422 `plan_empty`, a 403 and a 400 make **0** calls. The
`/integrations/**` rate limit (60/min per user+client) also caps the rate.

## What changed

### 1. `POST /integrations/v1/shopping-lists/active/from-plan` (new)

| | |
|---|---|
| Scopes | `shoppinglist.write` (existing URL matcher, unchanged) **and** `mealplan.read` (checked in the controller from the token's `SCOPE_` authorities, before the idempotency record; 403 problem+json otherwise) |
| Headers | `Idempotency-Key` required; `If-Match` not used |
| Body | `{"week": "current"\|"next"}` (case-insensitive). Missing or blank is 400 (bean validation); another value is 400 |
| Empty week | No plan, or the plan yields nothing to buy (checked with `ShoppingListGenerator#hasItems`, no LLM): **422** problem with `"code": "plan_empty"`. Nothing is written, and the active list is not created |
| Effect | `ShoppingListService#ensureActive` (MF3, under the per-user lock). Then, as the app does: `preparePlan` loads the recipes and makes the one normalization call; `mergePrepared` runs `ShoppingListGenerator#mergePlanCounting` (portion scaling, merge rules, checked lines never merged into) and `applyCategories`. The list's `items`, `weeklyPlanId` and `title` (kept if set, else the app's `"Week N Shopping List"`) are written with `Versioning.compareAndSet`. If the list changed meanwhile, it is re-read and re-merged, up to 3 attempts, then 412 |
| Response | **200**, the list exactly as `GET /shopping-lists/{id}` plus `added` and `merged`; `ETag` = the list's version |
| Replayed key | The first response, with `Idempotency-Replayed: true`. The plan is not added again |
| Deleted recipe in the plan | 400, as in the app (`ShoppingListValidationException`), nothing written |

`added` is the number of new lines. `merged` is the number of existing lines the plan's items went into:
amounts summed, an amount given to a line that had none, or an amount-less duplicate absorbed.
`ShoppingListGenerator#mergePlanCounting` is new. `mergePlan` now delegates to it and returns the same
items; `ShoppingListGeneratorCountingTest#sameResultAsMergePlan` pins that.

The app's own `createOrMerge` is **unchanged**. The new `ShoppingListService` methods (`preparePlan`,
`mergePrepared`, `titleForPlan`) call the same generator, normalizer and resolver in the same order.

### 2. `PATCH /integrations/v1/meal-plans/{planId}/entries/{entryId}` (new)

| | |
|---|---|
| Scope | `mealplan.write` (existing matcher for non-GET `/meal-plans/**`, unchanged) |
| Headers | `Idempotency-Key` required; `If-Match` with the plan's ETag, honoured as on the other plan writes (optional, like them) |
| Body | `{"day"?, "section"?}`: at least one (`{}` is 400). `day` uses the add-entry rules (`thursday`/`Thu`/`THU` → `THU`; others 400). `section` matches the plan's sections case-insensitively and the plan's spelling is stored; blank is 400, unknown is **422** `"code": "unknown_section"` |
| Checks, in order | plan (404, also another user's), `If-Match` (412), entry (404), section (422) |
| Effect | Only `day`/`section` change. The id, recipe, title, portions, notes, items and the entry's place in `entries` are kept. Compare-and-set on the plan. A no-op move writes nothing (same ETag) |
| Response | **200**, the plan as `GET /meal-plans/{week}` with the new `ETag` |
| Out of scope | Moving across weeks |

The brief asks for 422 on an unknown section. Adding an entry to an existing plan with an unknown section
is still **400**, as before; that status is not changed.

### 3. `MealPlanEntryDto`: `items`, `extraItems`

Two read-only string arrays at the end of the entry, never null (`[]`), copied from `PlanEntry`. Every
response that carries a plan includes them (GET, POST entries, DELETE, PATCH). Nothing can set them through
the API.

### 4. Problem `code`

`IntegrationApiException` gets an optional `code`, which the integration handler adds to the problem as
`"code"`. Only the two new 422s use it. Existing problems are unchanged.

## Request and response shapes (for MF4-pos)

```http
POST /integrations/v1/shopping-lists/active/from-plan
Authorization: Bearer <token with shoppinglist.write + mealplan.read>
Idempotency-Key: <uuid>
Content-Type: application/json

{"week":"current"}
```
```json
// 200, ETag: "1794146963391"
{ "id": "6720…", "title": "Week 46 Shopping List", "status": "active",
  "items": [ { "id": "…", "name": "Köttfärs", "quantity": 500.0, "unit": "g", "checked": false, "category": "meat" },
             { "id": "…", "name": "Salt", "quantity": null, "unit": null, "checked": false, "category": "pantry" } ],
  "updatedAt": "2026-11-08T14:09:23.391Z", "version": 1794146963391,
  "added": 5, "merged": 0 }

// 422 (nothing planned / nothing to buy)
{ "type": "about:blank", "title": "Unprocessable Content", "status": 422,
  "detail": "The week's meal plan has nothing to put on a shopping list",
  "path": "/integrations/v1/shopping-lists/active/from-plan", "timestamp": "…", "code": "plan_empty" }
```
Other outcomes:
- **403** if either scope is missing.
- **400** for a bad or missing `week` or a missing key, or when a planned recipe was deleted.
- **409** if the key is still in flight, or the active-list lock is busy (MF3).
- **412** after 3 concurrent-change retries.
- **422** if the key was reused with a different body.

Calling the route again with a **new** key adds the plan a second time (amounts double), as pressing the
app's button twice does. Retry with the **same** key.

```http
PATCH /integrations/v1/meal-plans/{planId}/entries/{entryId}
Authorization: Bearer <token with mealplan.write>
Idempotency-Key: <uuid>
If-Match: "<plan version>"
Content-Type: application/json

{"day":"thursday"}            // or {"section":"Lunch"} or {"day":"FRI","section":"Breakfast"}
```
```json
// 200, ETag: "<new plan version>"
{ "id": "…", "weekStart": "2026-11-02", "sections": ["Breakfast","Lunch","Dinner"],
  "entries": [ { "id": "…", "day": "THU", "section": "Dinner", "recipeId": "…", "customTitle": null,
                 "title": "Tacos", "notes": "extra ost", "portions": 2, "items": [], "extraItems": [] } ],
  "updatedAt": "…", "version": 1794146963456 }

// 422 unknown section
{ "status": 422, "detail": "section must be one of: Breakfast, Lunch, Dinner", "code": "unknown_section", … }
```
Other outcomes:
- **404** for an unknown or another user's plan or entry.
- **412** for a stale `If-Match`.
- **400** for `{}`, a bad day, a blank section or a missing key.
- **403** without `mealplan.write`.

How Personal OS can resolve "flytta tacos till torsdag":
1. `GET /meal-plans/current`.
2. Pick the entry by `title`.
3. PATCH it with `If-Match` set to the GET's `ETag`.

For "what does the dinner need", use the entry's `items`/`extraItems` plus the recipe's ingredients
(`GET /recipes/{recipeId}`).
