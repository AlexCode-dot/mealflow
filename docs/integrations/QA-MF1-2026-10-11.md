## N1: Authorization server. **ACCEPT**

Verified by test (A = author suite, Q = QA suite):

- **PKCE.** PKCE is required, S256 only. A missing challenge and `plain` are both refused (A). A wrong verifier gets `invalid_grant` (A).
- **Exact redirect URI.** Nine look-alikes are refused and none is redirected to (Q):
  - trailing slash
  - suffix
  - `/../`
  - added query
  - fragment
  - https instead of http
  - `localhost` instead of `127.0.0.1`
  - host-suffix trick
  - userinfo trick

  The token exchange is also refused when `redirect_uri` differs or is missing (Q). One gap was not tested: Spring Authorization Server allows any port on a *loopback* redirect URI (RFC 8252 §7.3). That only matters if a loopback URI is ever registered in production; production should register only the https Personal OS callback.
- **Client.** Exactly one client is registered, and only when id, secret and redirect URIs are all set (`OAuthClientProperties.isConfigured`). The secret comes from the env variable `PERSONAL_OS_OAUTH_CLIENT_SECRET` and is kept hashed in memory.
  - Scan of branch history (`git log -p d5f06b2..5fa6d52e`): no secret or private key committed. The only value found is the synthetic `test-only-client-secret` in `application-test.properties`.
  - A wrong secret gets 401, and so does use as a public client (client_id, no secret). A failed attempt does not burn the code (Q).
- **Consent.** Consent is required and can be denied (A). Partial consent issues only the approved scopes (Q). Adding scopes to the consent POST that were not requested does not widen the grant (Q).
- **Scopes.** An unknown scope at authorize is refused (Q). A refresh that asks for a wider scope gets `invalid_scope` (Q).
- **Response types.** `response_type=token` (implicit) is refused, and no token appears in a redirect (Q).
- **State and codes.** `state` round-trips (A, Q). Codes are single-use, and replaying one revokes the grant (A). Codes live 5 minutes or less and are marked invalidated after use (Q).
- **Refresh tokens.** They rotate. Reusing a retired refresh token deletes the whole family, so the new refresh token also fails (A, Q). A `security.token_reuse_detected` audit event is written, and no audit document contains any access or refresh token value (Q).
- **Revocation.** Revoking a refresh token (A) or an access token (Q) marks the grant `revoked`. The revoke endpoint requires client authentication (A).
- **Token lifetimes.** Access token: `exp - iat` ≤ 300 s. Refresh token: 30 days or less (Q).
- **Token claims.** `iss` equals `jwt.issuer`, `aud` is `mealflow-integrations`, `sub` is the user id, `client_id` is set, and there is no email claim (Q). Grant documents hold only hashes, never token values (A, Q).

Non-blocking observations:

- **O1.** `/oauth2/introspect` (a library default endpoint) is enabled but not documented in the contract, and has no rate limit (`RateLimitFilter` covers token, revoke and authorize only). Either disable it or rate-limit it.
- **O2.** Revoking at `/oauth2/revoke` keeps the stored consent. A browser that is still logged in to the OAuth pages can therefore re-authorize the same scopes without a consent screen. This is standard library behaviour. Disconnecting from MealFlow (`DELETE /account/connections/{clientId}`) does remove consent.

## N2: Existing auth not weakened. **ACCEPT**

- **First-party code.** Unchanged except two additions:
  - identity `SecurityConfig` adds a *stricter* validator: tokens with an `aud` or `client_id` are rejected on the first-party API.
  - It adds an authenticated `/account/connections` route.

  app-api `/api/**` adds the same `FirstPartyTokenValidator`. An integration token on the first-party API gets 401, and the account is not deleted (A).
- **OAuth login.** It checks the same things as `AuthService.login` (argon2 password, verified email), plus disabled and deleted accounts.
  - Disabled and deleted accounts get the generic error (Q).
  - Unverified accounts go to the email-code step and get no consent and no code (Q).
- **CSRF.**
  - A login POST without a CSRF token gets 403 and does not authenticate (Q).
  - Consent forgery is blocked by the library's server-side consent `state` (the authorize endpoints are library-owned and exempt from CSRF). A forged state, Alice's state submitted in Bob's session, and a state replayed without a session cookie all produce no code (Q).
- **Sessions.** The session id rotates on login, so there is no session fixation (Q). The OAuth browser session never authenticates the first-party API: `/auth/me`, `/account/connections` and `DELETE /account` with only the cookie are all refused (Q).
- **Rate limits.**
  - `/oauth/login`, `/oauth/signup`, `/oauth/verify` and `/oauth/verify/resend` share the existing login, register and verify buckets.
  - `/oauth2/token`, `/oauth2/revoke` and `/oauth2/authorize` have their own buckets (A: `OAuthRateLimitIT`).
- **Observation O3.** On app-api `/integrations/**`, `RateLimitFilter` runs *after* `BearerTokenAuthenticationFilter`, so requests with invalid tokens are not counted. They cost one signature check each. Low risk.

## N3: Resource server. **ACCEPT**, with one correction carried under N4

- **Token validation.** Issuer, audience, expiry, signature and grant activity are all enforced.
  - The author suite covers wrong `aud`, missing `aud`, expiry, wrong `iss`, unknown, missing, revoked or deleted `gid`, and a grant belonging to another user (A).
  - QA adds `alg:none` (401), a token signed by a foreign key with the same `kid` (401), a future `nbf` (401), an `aud` list without `mealflow-integrations` (401), and a token passed as `?access_token=` (ignored, 401) (Q).
- **Scope matching.**
  - Read scope cannot write. QA tried path variants (trailing slash, `//`, `/../`, `;x=1`, upper case, percent-encoding) plus PUT and DELETE; none produced a 2xx.
  - A write scope for one area does not grant writes in another (Q).
  - A write scope alone does not grant reads (A).
- **Cross-user isolation.**
  - Bob cannot read, add to, check or remove items on Alice's shopping list. He gets 404 and her list is unchanged (Q).
  - Bob cannot plan Alice's recipe (400, title not disclosed) or delete Alice's meal-plan entry (404) (Q).
  - Responses never include the owner's user id (Q).
- **Idempotency.**
  - Keys are scoped per user and client (A).
  - The same key on a different endpoint gets 422, with no replay and no write (Q).
  - The same key after a reconnect (new grant, same user and client) replays instead of creating a duplicate (Q).
  - Failed writes release the key (A).
- **ETag and If-Match.** A stale `If-Match` gets 412 and writes nothing, on recipe PATCH, shopping-list item POST/PATCH/DELETE, and meal-plan entry POST/DELETE (Q). Writes are compare-and-set in Mongo.
- **Error bodies.** Malformed JSON, oversized fields, type mismatches, odd ids, bad `limit`/`cursor` values, invalid week values, unknown ids and garbage tokens all return problem+json 4xx bodies. None mentions `Exception`, a package name, a stack frame or "mongo" (Q).
- **Audit.** The `integration_audit` log line carries userId, clientId, gid, method, path and status, and no token.
- **Status for unsupported requests.** An unsupported method (PUT on `/recipes`) and an unsupported media type (`text/plain`) return **500 "Unexpected error"** instead of 405/415. The body is still closed and has no internals, so the N3 wording holds. The status is wrong, though, and a connector would treat it as a retryable server error. It is recorded as drift D6 under N4.

## N4: Contract. **REJECT**

The contract (`personal-os-v1.md` and `.openapi.yaml`) does not match the implementation. Personal OS's C2 connector is built from the contract, so the breaking drifts must be fixed either in the code or in the contract.

**Breaking drifts, confirmed by `QaMf1ContractConformanceIT` (red):**

| # | Contract | Implementation | Where |
|---|---|---|---|
| D1 | Meal-plan entry `day` is `"monday"` / `"tuesday"` (md examples) | Only `MON`…`SUN` accepted, and returned as `MON`. The contract's own example request gets 400. | `IntegrationMealPlanService` ~l.43, 87-90 |
| D2 | `Ingredient.name` maxLength 120 (yaml) | `@Size(max = 80)`, so 81-120 characters gets 400 | `recipes/web/dto/IngredientDto.java` |
| D3 | `Ingredient.quantity` is number or null and `unit` is optional (yaml) | `quantity` must be > 0, and `unit` is required whenever `quantity` is set. Neither rule is documented. | `IngredientDto.java` |
| D4 | "Every resource response carries an `ETag`" (md) | `GET /meal-plans/{week}` for an empty week sends no ETag (`id`/`version` are null) | `IntegrationMealPlanController` ~l.43-45 |
| D5 | Status list in md | An unsupported method gets 500 instead of 405 | global `ApiExceptionHandler` catch-all |
| D6 | Status list in md | An unsupported media type gets 500 instead of 415 | same |

**Further drifts found by reading the code (not pinned by tests):**

- **D7 (contract defect).** In the yaml, `UpdateRecipe` is `allOf: [CreateRecipe]` plus `required: []`. `allOf` keeps CreateRecipe's `required: [title]`, so a generated client would force `title` on PATCH. The code treats every field as optional.
- **D8 (undocumented `section` rule).** The md example uses `"Middag"`. A new plan defaults to `Breakfast`/`Lunch`/`Dinner`, and on an existing plan `section` must be one of that plan's sections.
- **D9 (undocumented `recipeId` rules).** "Exactly one of `recipeId` / `customTitle`" is enforced but not documented. A foreign or unknown `recipeId` gets 400, not 404.
- **D10 (minor):**
  - Shopping item `category` is emitted in lower case; the example shows `"DAIRY"`.
  - `GET /shopping-lists?status=` is undocumented.
  - `Location` headers on POST are undocumented in the yaml.
  - Problem bodies carry extra fields (`errors[]`, `retryAfterSeconds`, `param`, `value`).
  - `client_id` is shown as literally `personal-os`, but it is whatever `PERSONAL_OS_OAUTH_CLIENT_ID` is set to.

These match the contract:

- paths and methods
- scope per endpoint
- recipe paging (`limit` 1-100, opaque `cursor`)
- the other body limits
- response DTO fields
- idempotency semantics (400 / 422 / 409 / replay headers / 24 h)
- ETag and `version` format
- If-Match (optional, `*` accepted, 412)
- rate limit (60/min per user and client, 429)
- OAuth endpoints, scopes, lifetimes and claims

## N5: User control and i18n. **ACCEPT**

- **Controls.**
  - MealFlow app: Settings → "Connected apps" (`ConnectedAppsScreen`) lists connections with their permissions and has a remove action.
  - Backend: `GET` / `DELETE /account/connections[/{clientId}]` (A).
  - Disconnecting affects only the caller's own grants, and Bob's are untouched. An unknown client gets 404. Account deletion removes all grants (Q).
- **i18n.** The Expo locales `en.ts` and `sv.ts` add the same keys. The server-rendered OAuth pages have the same 38 keys in `messages.properties` and `messages_sv.properties` (`OAuthMessagesTest` (A) plus a QA key diff). The consent screen names each scope in plain Swedish and English (A).
- **Audit.** Consent, token issue, revocation, user revocation and reuse detection are all audited, without token values (A, Q).

## Minimum corrections to reach ACCEPT

1. **Contract and code alignment (N4).** For D1-D4, change either the contract or the code so they agree. Recommended:
   - D1: accept `monday`…`sunday` (case-insensitive) as the documented form, or document `MON`…`SUN` and fix the examples.
   - D2: set the yaml `Ingredient.name` maxLength to 80, or raise the DTO limit to 120.
   - D3: document `quantity > 0` and "`unit` is required with `quantity`" in the yaml.
   - D4: document that an empty week has no ETag, or emit an ETag such as `"0"`.

   Then update `QaMf1ContractConformanceIT` to the agreed contract and make it green.
2. **Error statuses (D5/D6).** Map `HttpRequestMethodNotSupportedException` to 405 and `HttpMediaTypeNotSupportedException` to 415 (and `HttpMediaTypeNotAcceptableException` to 406) as problem+json. Add both to the contract's status list.
3. **Contract fixes (D7-D9).** Make `UpdateRecipe` a standalone schema with no required fields. Document the `section` rule and the `recipeId`/`customTitle` exclusivity, including that the error is 400.
4. **Optional follow-ups.** O1 (disable or rate-limit introspection), O3 (count invalid-token requests), and D10 (minor contract gaps).
